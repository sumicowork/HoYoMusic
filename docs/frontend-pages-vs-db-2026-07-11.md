# 前端各页 × 真实数据库 对照分析（2026-07-11）

> 数据基准：`hoyomusic_import`（从你下载的包还原，3594 首 / 146 专辑 / 8 游戏 / 26125 credits）。只读分析，未改代码/数据。
> 目的：判断每个页面"设置得合不合理"——不只看代码显示什么，更看**真实数据库能否喂饱它**。

---

## 0. 方法

对 `frontend` 每个页面，查它依赖的数据在真实库里的**填充率与关联完整性**，判断页面"在干什么"是否对得上真实内容。本分析**诚实纠正了上一轮纯代码审计的 3 处误判**（见 §3）。

## 2. 逐页：在干什么 × 数据库实际 × 是否合理

**`/` 首页** — 随机专辑/歌曲轮播 + 热门 Top10 + 游戏卡片。
- 随机内容数据充足 ✓；**热门 Top10 依赖 `play_count`，全库为空 → 该区块永远空/假** ✗；游戏卡片含 2 个 `unreleased` 且无专辑的游戏，点进去是空页 ✗。
- 判断：⚠ **热门块是空转功能；未发行游戏不该进首页/导航**。

**`/library` 曲库** — 3594 首曲目表。全字段有数据 ✓。判断：✓ **合理（全站最稳）**；仅未登录按钮"消失"问题（前报）。

**`/albums` 专辑** — 146 专辑网格。全有 `game_id`，可按游戏筛选（数据支持，页面未做）✓。判断：✓ **合理**，建议加游戏筛选侧栏。

**`/albums/:id` 专辑详情** — 沉浸式 Hero + 按碟曲目。数据全 ✓。判断：✓ **优秀**（前报）。

**`/artists` + `/artists/:name` 艺术家** — 由 `track_credits` 字符串推导。3133 首有 credits，数据丰富 ✓；但**无 artists 实体表、id 用名字编码、改名即断链**（已知脆弱）。判断：⚠ **数据够用但数据模型脆弱**，长期必须补 `artists` 表（DB 批判 P0）。

**`/tags` + `/tags/:id` 标签** — 分组折叠树 + 面包屑。
- `tag_groups` 只有 `BPM`(97)+`人声类型`(3)，**本质是数值属性而非分类标签**；用户想按"游戏/场景/角色"找歌，标签里没有。
- `TagDetail` 面包屑依赖"层级标签（游戏/原神/主题曲）"，**真实库里不存在这种层级 → 面包屑是空壳**。
- 判断：✗ **标签维度设计偏离用户真实需求**，是"看起来有、实际没用"的功能。

**`/games/:id` 游戏详情** — 仅专辑网格。
- `games` 表有 `description`/`cover_path`/`status` **可用但页面没显示**；2 个 `unreleased` 游戏 0 专辑→空白页；无"游戏歌曲直览"（数据可经 album join 支持，未做）；英文 fallback。
- 判断：✗ **最不合理**——既有数据浪费，又有空页与英文残留。

**`/track/:id` 歌曲详情** — Hero + 歌词/创作/音源。
- 歌词：**无歌词表 → 永远空** ✗；创作 87% ✓；音源 42% ⚠（过半无音源）；规格 100% ✓。
- 判断：⚠ **歌词块空转、音源覆盖低**，但主体合理。

**`/search` 搜索** — 多维筛选（游戏/艺术家/年份/时长/标签）。游戏筛选需 `tracks` 经 album join（后端若支持则可行）；标签筛选=BPM/人声类型，**价值低**。判断：⚠ **功能完整但筛选维度价值参差**。

**`/me` + `/playlists`** — 收藏/歌单。数据极少（内测常态）✓。判断：✓ **合理**。

**`/admin/analytics`** — 访问/播放统计。`visit_logs` 10 万（访问维度丰富 ✓）；`play_count` 全空、`play_events` 仅 3937 → **播放维度失真**。判断：⚠ **播放统计不可信**，应标注"数据待累积"或暂隐播放图表。

## 3. 诚实纠正上一轮纯代码审计的 3 处误判

1. 前报称 `TrackDetail` "歌词点击 seek 是亮点"——**错**：库里无歌词表，该块永远空。
2. 前报称 `TagDetail` "面包屑对层级标签（游戏/原神/主题曲）表达清晰"——**错**：真实 `tag_groups` 只有 BPM/人声类型，无此层级，面包屑为空壳。
3. 前报称 `tag_groups=3`——**错**：实际仅 2 组。

---

## 4. 设置不合理的核心结论（按严重度）

- 🔴 **空转功能（页面有、数据无）**：热门 Top10（play_count 全空）、歌词块（无表）、TagDetail 面包屑（无层级标签）。
- 🔴 **游戏详情页最弱**：浪费 description/cover/status、unreleased 游戏空页、无歌曲直览、英文残留。
- 🟡 **标签维度错配**：BPM/人声类型不是用户要的分类，应按"游戏/场景/角色/风格"重建标签体系（或改用 music_source 树做主分类）。
- 🟡 **播放统计失真**：play_count 未回写，analytics 播放维度不可信。
- 🟢 **稳的页**：曲库、专辑、专辑详情、个人中心——可当重设计基线。

---

## 5. 给重设计的启示

- 首页"热门"要么接真实播放事件（需后端修 play_count 回写），要么改为"编辑推荐 / 最新入库"。
- 游戏详情必须做 Hero + 歌曲直览（join album），并过滤 `unreleased` 游戏出首页/导航。
- 标签体系要么重构为有意义的分类（配合 DB 补标签），要么让"游戏/专辑/艺术家"承担分类职责、把 BPM/人声类型降级为歌曲属性筛选。
- 歌词是内容缺口：要么导入歌词数据，要么从 UI 移除该块避免"永远空"。
- 播放统计：要么后端修回写，要么 analytics 暂隐播放维度、只保留访问维度。
