# HoYoMusic Windows Client Roadmap (2026)

## 1. 目标与边界

### 1.1 产品目标
- 将 Windows 客户端建设为“游戏音乐档案馆”，核心路径为：`游戏 -> 专辑 -> 曲目 -> 播放`。
- 保持轻量 Spotify 式发现体验（推荐、连续播放、队列、收藏、歌单），但不做后台工具型 UI。
- 在 WinUI 3/Windows App SDK 上实现稳定、可发布、可持续迭代的桌面体验。

### 1.2 强约束（必须遵守）
- API 与数据语义严格对齐 `backend/` 与线上 `https://music.hoyodb.com`。
- 不新增/猜测后端字段，不改变 `{ success, data?, error? }` 响应契约。
- 行为优先参考线上，其次 `frontend/`，最后才是接口文档推断。
- Admin 仅作为权限分支，不作为主入口。

### 1.3 非目标（当前周期不做）
- 不重写后端业务逻辑。
- 不引入新的后端协议或私有桌面专用接口。
- 不做与 Web 端语义冲突的“桌面特供业务规则”。

## 2. 设计与工程原则
- **Web-Truth First**：业务语义以 `frontend/src` 和 `backend/src` 为真相源。
- **契约优先**：先校验 DTO 与错误处理，再做 UI。
- **闭环交付**：每个迭代必须有可演示链路与验收清单。
- **稳定性优先于花哨**：先修崩溃/错误恢复，再做体验增强。
- **可回滚**：所有大改动都需可快速降级。

## 3. 版本阶段规划（10 个月，5 个阶段）

## Phase 0（已进行）: 稳定化与信息架构重整（M0）
### 目标
- 从 PoC 管理感界面迁移到“档案馆”信息架构。
- 修复高频 UI 崩溃和关键交互缺失。

### 完成定义（DoD）
- 关键页面路径可走通：发现 -> 专辑详情 -> 曲目播放。
- 底部播放器具备进度拖动与基础队列切换。
- 高优先级崩溃可复现、可定位、可修复。

### 风险
- WinUI XAML 模板改动导致运行时崩溃。
- 列表容器复用导致图标/状态显示异常。

## Phase 1: Web 行为对齐与播放闭环（M1-M2）
### 目标
- 完成桌面端核心行为与 Web 端一致化。

### 范围
- 鉴权与会话：登录、登出、鉴权失效恢复（401）。
- 发现/游戏/专辑/曲目：严格按现有接口结构渲染。
- 播放：`sequence/loop/shuffle/single` 完整语义对齐。
- 队列：点击替换队列、next/prev 边界一致。
- 播放上报：对齐 `POST /api/public/tracks/:id/play`。

### 技术任务
1. 建立 API 错误映射层（异常到 UI 中文提示）。
2. 梳理 `TrackService/GameService/AlbumService` DTO 对齐矩阵。
3. 对齐 `frontend/src/store/playerStore.ts` 的模式与索引规则。
4. 统一空态/错误态/加载态模板。
5. 增加契约回归测试（服务层）。

### 验收标准
- 核心路径链路全部可用，且与 Web 行为一致。
- API 错误提示统一，且不出现未处理异常弹崩。
- 非管理员看不到管理入口。

### 风险与缓解
- **风险**：线上字段偶发缺失。
  - **缓解**：所有关键字段容错 + 日志记录。
- **风险**：播放边界行为与 Web 偏差。
  - **缓解**：建立播放模式对照测试清单。

## Phase 2: 下载与离线能力（M3-M4）
### 目标
- 下载功能从“队列展示”升级到“真实执行 + 可恢复”。

### 范围
- 下载任务创建、暂停/恢复、取消、失败重试。
- 任务状态持久化（重启后恢复）。
- 基础离线播放入口与资源校验。

### 技术任务
1. 扩展 `IDownloadService`，实现真实下载执行器。
2. 下载任务持久化（本地存储与恢复）。
3. 文件完整性校验与错误恢复策略。
4. 下载 UI 与状态机对齐。

### 验收标准
- 重启应用后，下载任务可恢复。
- 网络中断恢复后可继续下载。
- 下载失败有明确错误信息与重试入口。

### 风险与缓解
- **风险**：Windows 权限/目录问题。
  - **缓解**：下载目录预检 + 用户可配置路径。
- **风险**：大文件中断导致损坏。
  - **缓解**：分片/断点 + 完整性校验。

## Phase 3: 稳定性与可观测性（M5-M7）
### 目标
- 让客户端在真实网络环境下稳定运行并可诊断。

### 范围
- 统一日志体系（启动、网络、播放、下载）。
- 错误分级与恢复策略（瞬时错误自动重试）。
- 性能优化（列表滚动、封面加载、UI 卡顿）。

### 技术任务
1. 引入结构化日志与日志轮转。
2. 为关键服务加超时/重试/退避策略。
3. 封面加载缓存策略对齐 Web 体验。
4. 增加崩溃归因信息（便于快速止血）。

### 验收标准
- 常见故障可通过日志定位。
- 启动与切页稳定，无高频闪退。
- 高负载下 UI 交互可接受。

### 风险与缓解
- **风险**：重试放大流量。
  - **缓解**：指数退避 + 最大重试次数。
- **风险**：日志包含敏感信息。
  - **缓解**：统一脱敏规则。

## Phase 4: 发布与更新闭环（M8-M10）
### 目标
- 建立可控发布流程与升级体验。

### 范围
- MSIX 分发规范化。
- 更新通道（Beta/Stable）与灰度策略。
- 升级失败回滚与版本兼容策略。

### 技术任务
1. 自动化打包与签名流程。
2. 更新策略与版本元数据管理。
3. 发布闸门（构建、测试、冒烟、回滚演练）。

### 验收标准
- 可稳定安装、升级、回滚。
- 发布质量可追踪、可评估。

### 风险与缓解
- **风险**：升级破坏现网用户体验。
  - **缓解**：先 Beta 灰度再 Stable。

## 4. 与 Web 对齐清单（持续执行）

### 4.1 后端契约核对
- `backend/src/routes/publicRoutes.ts`：公开曲目、播放、封面、下载。
- `backend/src/routes/authRoutes.ts`：登录与会话。
- `backend/src/controllers/*`：返回结构与错误语义。

### 4.2 前端行为核对
- `frontend/src/store/playerStore.ts`：播放模式与队列规则。
- `frontend/src/services/api.ts`：鉴权、401 处理、请求头策略。
- `frontend/src/services/trackService.ts`：曲目读取/播放相关行为。
- `frontend/src/pages/*`：Discover/Album 交互路径与状态展示。

### 4.3 验证口径
- 同一账号、同一曲目、同一行为，桌面端结果应与 Web 一致。
- 不一致默认视为桌面缺陷，优先修复而非“产品差异”。

## 5. 研发节奏与交付机制
- 采用 **2 周一个迭代**。
- 每迭代固定交付：
  1. 1 条完整用户链路改进。
  2. 1 组契约对齐测试。
  3. 1 组稳定性改进（崩溃/日志/恢复）。
- 每阶段结束输出：
  - 演示版本
  - 差异清单（与 Web）
  - 风险与下一阶段范围冻结

## 6. Phase 1 详细 Backlog（立即执行）

## Sprint 1（第 1-2 周）
1. 整理服务层契约矩阵（接口、字段、错误码、对应 UI）。
2. 统一 API 异常映射与中文提示（登录、播放、收藏、歌单）。
3. 对齐播放模式与队列边界规则（含单曲循环/随机）。
4. 增加服务层契约测试（优先 Track/Favorite/Playlist）。

### 验收
- 核心接口调用失败时，UI 给出清晰中文提示，不闪退。
- 队列行为与 Web 对照用例一致。

## Sprint 2（第 3-4 周）
1. 对齐播放上报与最小播放时长策略。
2. 完整覆盖 Discover/AlbumDetail 的空态、加载态、错误态。
3. 补齐管理员入口权限显示一致性回归。
4. 输出阶段报告：已对齐项、未对齐项、阻塞项。

### 验收
- 播放上报稳定，失败时不影响播放主流程。
- 页面状态一致，用户可理解当前系统状态。

## 7. 质量门禁（每次提交必须满足）
- `dotnet build` 成功。
- 相关测试通过（新增逻辑必须有测试）。
- 变更说明中明确“与 Web 对齐点”。
- 不引入新 API 语义或字段。

  1. 先完成“服务层契约矩阵”文档。
  2. 随后实现“统一 API 异常映射层”。
  3. 再做“播放模式边界回归测试”。
